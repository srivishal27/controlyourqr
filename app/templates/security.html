Security

How this site is built, how to check it, and how to report a problem.

Version {{ app_version }}

Threat model

The asset being protected is the content a user encodes: private URLs, Wi-Fi credentials, personal contact details. The adversary we design against is the operator of the website itself (that is, us), plus anyone who compromises it, and any third party we might otherwise have invited onto the page.

The mitigation is structural rather than procedural: the encoding happens client-side, and the browser is instructed to block the network paths that exfiltration would need. A promise not to look is worth little; removing the ability to look is worth a great deal.

Response headers

  • Content-Security-Policy. default-src 'self' with connect-src 'none', object-src 'none', base-uri 'none', form-action 'none' and frame-ancestors 'none'. No unsafe-inline, no unsafe-eval, no nonces: every script and stylesheet is an external file on this origin.
  • Strict-Transport-Security. Two years, includeSubDomains, preload-eligible.
  • X-Content-Type-Options: nosniff and X-Frame-Options: DENY.
  • Referrer-Policy: no-referrer. We leak nothing to anywhere you navigate next.
  • Permissions-Policy. Camera, microphone, geolocation, USB, serial, payment and a dozen more are switched off at the platform level.
  • Cross-origin isolation. COOP: same-origin, CORP: same-origin, COEP: require-corp.

Supply chain

The site loads exactly two scripts, one stylesheet and one SVG icon, all from this origin. There is no web font service, no analytics snippet and no tag manager.

One honest caveat: Cloudflare fronts the domain as a CDN and DoS shield, so it is technically able to alter what it serves. Its content-modifying features (Web Analytics, Email Obfuscation, Rocket Loader and auto-minification) are switched off for this domain, and the Content-Security-Policy above would block an injected third-party script regardless. You can confirm the edge is serving what we published by comparing a response against the source.

  • The encoder is node-qrcode (MIT), pinned to an exact version and bundled from source with esbuild by tools/build-vendor.sh.
  • The bundle is committed to the repository, so the served bytes are reviewable in the diff rather than fetched at deploy time.
  • The Python side is Flask and gunicorn with pinned versions; the server holds no state, no database and no user input.

Verify it yourself

  • Load the generator, disconnect from the network, and confirm that generating and downloading still work end to end.
  • Open DevTools → Network and type into the fields. There are no requests.
  • Inspect the response headers and read the CSP for yourself.
  • Read app/static/js/app.js in the repository. It is unminified and commented, and contains no network calls.
  • Rebuild the vendor bundle with tools/build-vendor.sh and diff it against the committed file.

Reporting a vulnerability

Reports are welcome and will be taken seriously. Email {{ contact_email }} with enough detail to reproduce the issue. Machine-readable contact details are at /.well-known/security.txt per RFC 9116.

Please give a reasonable window to ship a fix before publishing. Testing against this site is fine as long as it is non-destructive and does not degrade the service for anyone else: no denial-of-service, no automated scanning at volume, no attempts against third-party infrastructure.

Known limitations

  • A QR code is a container, not a guarantee. This tool encodes exactly what you give it; it does not vouch for where a link leads.
  • Clipboard copy needs a secure context and a browser that supports ClipboardItem. Downloads are the portable path.
  • Very large payloads (long vCards, long text) may exceed the capacity of a single symbol at high correction levels. The tool tells you when that happens rather than silently truncating.
  • Client-side encoding means the security of your data is bounded by the security of your own device and browser.
